- **The prompt-independent graph startup summary was noise rather than context** ([REQ-AGENT-091](agents.md#req-agent-091-advanced-session-graph-first-runtime-reminders) former AC1 retired; former AC2 renumbered to AC1). The Claude `SessionStart[startup]` hook read only an `edges` key while canonical Graphify output carries `links`, so a real 34,961-link graph was announced as having zero edges and no key concepts. Correcting the key did not rescue the mechanism: highest degree selected generic duplicate labels rather than task-relevant architecture, ignored graph freshness, overlapped prompt-aware first-turn memory, and added persistent context before any user intent existed. - **A hook the sync restored stayed unspawnable until the next container boot** ([REQ-STOR-002](storage.md#req-stor-002-file-persistence-across-sessions) AC4 added, constraint added). R2 carries an object's content and modification time, not its POSIX mode, so any sync that rewrites a hook script drops the exec bit -- and a hook registered by bare path is spawned through its shebang, so it then fails with a permission error rather than doing nothing. The repair already existed but ran only on the entrypoint path, which is once per container, while the sync that undoes it runs every fifteen minutes: observed live as a container started at 21:29, a sync round rewriting the file at 22:02, and the next session boundary erroring. It now also runs after every successful bisync, the single choke point the periodic round, the vanished-file retry and the shutdown sync all pass through, so the window is seconds instead of the remainder of a cycle. Widened from the one extension observed failing to the script types a hook can be, since a user's own shell hook in that directory fails identically and just as silently. Recorded because the mode is the second attribute this store cannot round-trip to produce a live defect -- the provenance marker is the other -- and the general rule is what carries: re-establish locally whatever the store cannot carry, rather than assume it survived the trip.

- **Two orphans neither retirement mechanism could reach** ([REQ-STOR-019](storage.md#req-stor-019-seeded-files-are-marked-and-retired-ones-are-removed) AC8 added, constraint rewritten; [REQ-AGENT-099](agents.md#req-agent-099-agent-settings-and-plugins-assembled-at-container-start) AC6 added). Retirement has two routes: an object carrying a stale provenance marker, and the frozen pre-marker list compiled by walking the seed module's history. A file the container wrote itself and the sync then carried to R2 satisfies neither -- it never appears in that history, and the sync strips custom metadata, so no marker can describe it. `.claude/hooks/enforce-ctx-mode.sh` is that case: its content shipped as a seeded key under the context-mode plugin's scripts directory and was retired there correctly, while the copy at the legacy hooks path, placed by automation that no longer exists in the repository, outlived it in every bucket. The frozen list was the only route left, so the constraint forbidding appends is narrowed rather than broken -- a key the seed once shipped still never belongs there, and the list grows only for a product-generated file that was never a key at all, each entry shown to be product-generated rather than user-authored before it is added. The second orphan is `.claude/hooks/context-mode-cache-heal.mjs`, which context-mode's own installer writes to repair symlinks under a plugin cache this product never populates -- inert here, and visible only as the hook error that started this investigation. Its registration lives in each user's synced settings, so retiring the object alone would have traded a permission error for a missing-file one; the merge that already preserves user hooks while replacing managed ones now counts that registration as managed and drops it in the same release, and a user's own hook on the same event is asserted to survive it. Recorded because the sweep behaved exactly as designed: deletion requires positive evidence and a file indistinguishable from the user's own is kept, so the gap was in what evidence can exist, not in the rule.

- **Only one of the two runtimes was covered at the boundary, and the sections most worth carrying could vanish before they were carried** ([REQ-MEM-019](memory.md#req-mem-019-post-compaction-recall-of-recent-session-extracts) AC6 added, constraints extended). The recall existed for one runtime only; the other reaches the same boundary through a compaction event of its own and was left resuming from a summary of a summary exactly as before, so it now delivers the same digest as a message persisted in the session, and stays out of child sessions where a subagent's narrow context must not be flooded with whole-session history. Two implementations rather than one shared file because the injection surfaces genuinely differ -- one returns context from a session-start hook, the other sends a session message -- while the selection, the bounds and the injected wording are held identical. Two defects in the shared behaviour are closed at the same time: a section parser that flipped its fenced-block state on any backtick line let the inner fence of a nested block close the outer one, after which every later heading went unrecognised and the decisions section -- the content this exists to carry -- was silently dropped; and the per-extract bound was spent in code points while the budget it protects is bytes, so multibyte content overran it several times over. Recorded because both were invisible in testing: every fixture was plain ASCII, where the two bounds are indistinguishable, and an unbalanced fence produces no error, only a quietly shorter digest.

- **The unified graph is the only source first-prompt injection queries, in both runtimes** ([REQ-MEM-013](memory.md#req-mem-013-proactive-memory-injection-on-first-prompt) AC5 narrowed, AC7 added). A per-repo graph was accepted as a substitute when the unified one was missing or too large. It is not one: this fires at the start of a session, when no repo graph has been built yet, and once one has been the merger folds it into the unified graph, so the repo graph is only ever a smaller subset of what was already available. Treating it as a fallback bought nothing and made the injected context depend on which directory the session happened to start in. Both runtimes now read the unified graph or inject nothing, leaving the session sentinel unspent so a later prompt can try again. The two promises AC5 had come to carry are separated: which graph is read, and what happens when it is too large to read.

- **One runtime was handed its prior context and the other was merely told the context existed** ([REQ-MEM-013](memory.md#req-mem-013-proactive-memory-injection-on-first-prompt) AC6 added, constraint added). Pi received an announcement that the graph existed, how large it was and where it lived, and was left to decide to query it; the other runtime had the query run for it and the matching nodes placed in front of it before it answered. That is not a parity detail -- it decides whether prior decisions are present when the first answer is formed or merely reachable if the agent thinks to look. Pi now runs the same query on the first real prompt of a session, with the same keyword rule, the same ranking weights, the same node cap and the same one-shot sentinel that a miss does not spend, injected into the turn through the event that sits where the other runtime's hook sits. It additionally ignores synthetic prompts, which the hook runtime never delivers and the extension does. Recorded because the gap was invisible from the requirement alone: the criteria were all met, by one runtime, and nothing said the other was exempt.

- **First-prompt memory injection had silently stopped working once the graph it queries outgrew a guard meant to protect against a cost that never materialised** ([REQ-MEM-013](memory.md#req-mem-013-proactive-memory-injection-on-first-prompt) AC5 added, constraint added). The hook refuses a graph past a size ceiling, and the unified graph had grown past it, so every session had been starting with no injected prior context and nothing said so -- the failure mode of a fail-safe hook is silence, which is exactly what a working hook looks like from outside. The ceiling was set against a parse cost that measurement does not support: the graph that tripped it parses in well under a second inside a fraction of the memory budget, and the query already carries its own timeout, which is the real bound. The ceiling is therefore raised to a genuine memory guard and made overridable, and the skip is now specified to leave the session's one-shot sentinel unclaimed so a later prompt can still inject. Recorded because the lesson is about the guard, not the number: a limit that disables a feature outright, with no signal, is worse than the cost it was protecting against.

- **The byte bound now covers the notice that announces it, and a tied capture instant no longer depends on who read the directory** ([REQ-MEM-019](memory.md#req-mem-019-post-compaction-recall-of-recent-session-extracts) constraints added). The per-extract bound is the guarantee; when it is too small to also hold the truncation marker, the marker is dropped rather than the content, so the bound is never exceeded in order to say it was reached. Two extracts sharing a capture instant are ordered by name descending, so both runtimes agree on the tie instead of inheriting whatever order the filesystem offered. And the recall delivery is fail-silent as a whole rather than only in its reads, because it runs inside the runtime's own compaction dispatch, where a throw anywhere in the handler would surface in the session for a feature that is a convenience.

- **Recency for post-compaction recall now keys off the extract's captured instant, not the raw name text** ([REQ-MEM-019](memory.md#req-mem-019-post-compaction-recall-of-recent-session-extracts) AC2 restated). Sorting on the extract-name string broke across a UTC-offset change, since the name's text ordering no longer matched capture order; recency now derives the captured instant so the ordering holds regardless of offset or file-sync mtime rewrites. Earlier in the same work the byte-cap criterion and the truncation-marking guarantee it implied were separated into their own criteria, so each is independently anchored and tested rather than one criterion carrying two promises.

Three collections name the Claude rules that Pi absorbs, compacts, or covers by a skill, and one of the three was never checked against reality. A rule renamed or merged away left a key in it that matched nothing, so the rule stopped being excluded and flowed into Pi's instruction file in full — the exact opposite of what naming it there was for, with no error and no diff to notice. Every key in all three collections is now resolved against a real rule at build time, and a key that resolves to nothing fails the build naming the file and the collection it came from. The validation was previously one clause inside a requirement about the manifest pipeline, which is why it read as covered when only two of the three collections actually were.

- **A capture is bounded by what it costs, not by how many messages it holds** ([REQ-MEM-014](memory.md#req-mem-014-pi-capture-contract-transcript-prefilter-and-model-fidelity-lever) AC5 rewritten, Implemented; regression tests in `host/__tests__/prefilter-transcript-caps.test.js` and `src/__tests__/lib/agent-seed-pi-memory.test.ts`). Capture fires on a count of the user's prompts, fifteen, while the ceiling counted messages, forty. Those are different units and the rate between them is not fixed: measured, a conversational session produces about two and a half messages per prompt and an agentic one about twenty-five. So the ceiling either sat idle or cut a fifteen-prompt window down to the last nine of its prompts, and since the prompt counter advances whether or not the slice kept everything, what it cut was never offered to a later run. It was lost, not deferred. Counting messages also prices a two-hundred-character turn the same as a ten-thousand-character one, when characters are what the payload actually costs. The ceiling is now a character budget, spent newest-first, and spent on the user's prompts before the assistant's turns: the prompts are what the window is defined by and what the trigger counted, so a payload that drops them summarises a window without the instructions that produced it. Both passes stop at the first turn that does not fit, which keeps the budget a hard ceiling even in the case where the prompts alone would exhaust it. At two hundred thousand characters, half the previous worst case, an ordinary window is untouched and an agentic one keeps around two hundred turns where forty survived. The two runtimes reach the same selection on the same input, which is verified against fixtures rather than assumed from shared prose.

- **A memory capture now costs the same whether the session is short or enormous** (no acceptance criterion changed; regression tests in `host/__tests__/prefilter-transcript-caps.test.js`). Capture fires every fifteen prompts and hands the capture agent the conversation since the last one. Nothing bounded that payload, so it grew with the session: one resumed session produced fifty chunk files from a fifteen-thousand-line transcript and cost 220,000 tokens to summarise. Chunking was already there and was the wrong instrument — it bounds how much is in front of the agent at any instant, not how much passes through it in total, and the contract requires reading every chunk in order and forbids batching them. The two ceilings Pi has always had are now applied here as well: the payload as a whole is bounded, and any single turn longer than ten thousand characters is truncated. The per-turn ceiling is measured rather than guessed: across fifteen hundred real turns the median is under two hundred characters and the ninetieth percentile is under twenty-six hundred, so ten thousand touches only the top two percent and keeps almost nine tenths of all content. Capping the payload also collapses the chunk count, which is what keeps the per-chunk pass short. Truncation is allowed to cost prose but not citations: before a long turn is cut, the requirement ids, decision-record numbers, pull-request numbers and commit hashes it contains are collected, and any that fell past the cut are appended as a short trailing line. Those are the tokens that must be verbatim and the ones a later graph query searches on, so losing them to a byte count would defeat the point of capturing at all. A turn short enough to survive intact is byte-identical to an uncapped run. Both runtimes rescue, and to the same text, so a citation kept by one is never lost by the other. One of Pi's ceilings does not port the other way: Pi also caps the capture subagent's own loop at four turns and rejects any launch request that says otherwise, and a Claude agent definition has no field that can express that.

- **The push nudge and the turn-end gate resolve the review range through one function** (no acceptance criterion changed; regression tests in `host/__tests__/gh-pr-state.test.js`). Teaching the nudge to distrust GitHub's lagging pull-request metadata left the gate still trusting it, so the two consumers of the shared lane classifier could hand it different right-hand commits and reach different answers about which reviewers a push needs. Sharing the classifier function never delivered the agreement it was written for, because agreement also requires the same range going in. That mattered more once content-based reduction landed: a wider range is not always a superset in lane terms, since a commit that changes code and a later one that reverts it leave the wider range provably inert while the narrower one is not, so the nudge could ask for one reviewer while the gate demanded three. Head resolution now lives once, beside the pull-request state helper both hooks already share. The gate uses it for the range only and still acknowledges the head GitHub reports, which is the distinction that makes this safe: acknowledging a local commit the pull request does not yet carry would skip its review entirely once it was pushed.

- **The prover now has to say it proved something** ([REQ-AGENT-040](agents.md#req-agent-040-pr-boundary-lane-classification-and-agent-dispatch) AC5 split into AC5-AC7, all Implemented; regression tests in `host/__tests__/inert-source-delta.test.js`). Withholding two review lanes rested on a program exiting zero, which meant every way of reaching the end without deciding was indistinguishable from a proof. One such way was real: the guard that decides whether the file is being run or imported compared the module's own resolved path against the raw path it was invoked with, and Node resolves symlinks for the first but not the second, so a symlink anywhere in the install path skipped the whole program and exited zero. A behavioural change would have silently lost its specification and documentation reviewers with no error anywhere. The program now prints a token when, and only when, it has actually proven the delta inert, and both classifiers require that token rather than a bare exit status; the guard resolves symlinks on both sides as well, so the two defences are independent. Two smaller corrections landed with it: a regular expression written in statement position after a closing parenthesis was lexed as a division and its body scanned as code, which now simply fails to prove rather than guessing, and the per-file git calls were hoisted into one call for the whole range, since this runs at every turn end while a pull request is open.

- **The push gate says what it means** (no acceptance criterion changed; rule prose is intentionally not pinned by tests). The rule already forbade pushing while a review was incomplete, but a later sentence in the same file said that a finding of medium severity or above "means push and re-run immediately", and read alone that licensed exactly the push the gate forbids. Three pushes went out that way in one session, each invalidating the round already running and starting another against a head nobody had finished reviewing. The gate is now stated as absolute, names that no severity or reviewer instruction lifts it, separates committing (always allowed) from pushing (once per round), and requires naming the round that closed before each push. The severity sentence now defers to it explicitly.

- **Four holes in the freshly landed lane reduction, found by reviewing it** ([REQ-AGENT-040](agents.md#req-agent-040-pr-boundary-lane-classification-and-agent-dispatch) constraint tightened; stays Implemented; regression tests in `host/__tests__/lane-classifier.test.js` and `host/__tests__/git-push-review-reminder.test.js`). Reducing a comment-only push to the code lane made a fourth lane pair reachable — an inert source delta shipped alongside a documentation change — and the push nudge had no branch for it, so it fell through to the all-three directive and asked for a specification lane the turn-end gate then silently withheld. That disagreement between the nudge and the gate is the single thing the shared classifier exists to prevent, and it was eating part of the saving the reduction was for. The prover itself had a narrower but sharper hole: it compared file contents and never looked at the file mode, so making a file executable — or swapping a regular file for a symlink — left both blobs byte-identical and was proven inert, the one case where it called a real change nothing. It now reads the mode from the raw diff and refuses any change of it. Third, `LICENSE` counted as a documentation surface to the classifier but as source to both the packet builder and Pi, so a LICENSE-only push asked for the documentation lane, whose packet then owned none of the change and exited without reviewing anything; all three now agree. Last, the Pi copy of the composable-components skill still linked to a rule that had been absorbed into the constitution and is now actively deleted from every bucket, so Pi sessions were pointed at a document that no longer exists anywhere.


- **Pi reduces a comment-only push to the code lane too, by running Claude's prover rather than a copy of it** ([REQ-AGENT-040](agents.md#req-agent-040-pr-boundary-lane-classification-and-agent-dispatch) AC5 widened to both runtimes, Implemented; the constraint recording the divergence is replaced). The content-based reduction shipped for Claude alone, and the requirement said so: Pi kept running all three lanes on a comment-only range, deliberately and fail-closed, until the scanner could be ported. Porting it would have meant a second implementation of a JavaScript lexer in a second language, kept in agreement by a parity test — which is the arrangement the plan itself called the only way two copies could be kept honest, and therefore the reason not to have two. The prover instead moves into the directory the packet builder already made canonical, which the ordinary seed transform delivers to every runtime, and Pi's classifier shells out to it exactly as it already shells out to Git. There is one scanner, so there is nothing for it to disagree with. What can still diverge is the mapping from a proven-inert delta to a lane list, because that mapping is written twice — once in shell, once in TypeScript — so a test now runs the same four ranges through both and asserts the lane lists match. - **A preseed file that is retired now actually leaves the bucket** (no acceptance criterion changed; regression tests in `src/__tests__/lib/agent-seed-manifest.test.ts` and `src/__tests__/lib/r2-seed-mode.test.ts`). Seeding cleans up by deleting the keys the current build does *not* want in the active session mode, and it derives that list from the generated set — deliberately, because it never lists or scans the bucket. The consequence went unnoticed until three rules were folded into the engineering constitution: a file dropped from the manifest also drops out of the delete list, so nothing ever removes it and the container keeps loading it from a previous deploy. For a file whose content simply went away that is untidy; for one whose content moved into another file it is wrong, because the session then loads the same policy twice, once as the absorbed section and once as the stale standalone rule it was absorbed from. Retirements are now enumerated explicitly and deleted alongside the derived list, still subject to the guard that protects anything the current mode just wrote. They are applied where the deletes are issued rather than inside the derivation, because that function has an acceptance criterion of its own — it answers which keys of *this* build the current mode does not want, and a retirement is not one of them — so re-introducing a retired path later cannot delete the fresh copy. - **Rewording a comment no longer costs a full three-lane review** ([REQ-AGENT-040](agents.md#req-agent-040-pr-boundary-lane-classification-and-agent-dispatch) AC5 added, Implemented; one constraint replaced). The lane classifier decided which reviewers a push needs purely from the *names* of the changed files, so any file outside the specification and documentation trees meant all three lanes ran. A two-file comment-only push measured 241,870 tokens — 83% of what an eight-file one cost — to conclude nothing. Claude's classifier now also looks at the delta's *content*: when it can prove a source change is comments and whitespace, the specification and documentation lanes are withheld, because behaviour is unchanged and neither of those surfaces can have drifted. The code lane always runs. That is deliberate, and it is what makes a heuristic acceptable at all: whether a new comment is *true* is a code-review question, and a directive comment such as `@ts-expect-error` is precisely the case where a comment does change behaviour, so it still reaches a reviewer. Proving it needs a real scanner rather than a line-prefix rule, because a line beginning `//` can be text inside a template literal — true in the very file that prompted this. Both versions of the file are projected to a comment-free, whitespace-normalised form and compared, string and template bodies are copied verbatim, and a multi-line block comment is preserved as a line break because JavaScript treats it as one when inserting semicolons. Anything the scanner cannot resolve — a slash that might open a regular expression, JSX, an unterminated literal, a binary blob, an added or deleted or renamed file, an unsupported extension, or a missing runtime — is simply not proven, and the unreduced three-lane posture stands. Pi's classifier keeps running all three lanes for such a range; the divergence is one-directional and stated in the requirement.

## 2026-07-20

The frontend suite is sharded and gated on its JSON report like the backend already was, instead of being one unshielded `npm test`, and the completeness reconciliation now covers every suite rather than the backend alone.

The Workers pool no longer runs one test file at a time, and the aggregate job now fails when a backend test file present in the tree ran in no shard — the hole that serialization was never actually closing.

- **actionlint's version pin is bumped automatically** ([REQ-OPS-020](operations.md#req-ops-020-shadow-pin-version-bump-automation), [REQ-OPS-021](operations.md#req-ops-021-workflow-file-static-analysis); Implemented). The checksum-pinned actionlint binary is a shadow pin Dependabot cannot see; its weekly bump PR resolves and re-verifies the new checksum, so it needs no manual checksum step.

- **The workflow static-analysis audit now blocks merges** ([REQ-OPS-021](operations.md#req-ops-021-workflow-file-static-analysis); Implemented). zizmor and actionlint findings against workflow files fail the required `test` status context instead of only being recorded as advisory SARIF alerts, so a workflow defect can no longer merge on the strength of an alert nobody read.

- **CI checks run as parallel lanes and deploys reuse unchanged container images** ([REQ-OPS-001](operations.md#req-ops-001-deploy-workflow-trigger-and-pre-deploy-pipeline), [REQ-OPS-002](operations.md#req-ops-002-docker-image-build-vulnerability-scan-and-registry-push), [REQ-OPS-003](operations.md#req-ops-003-pr-checks-run-lint-test-typecheck-and-security-audit), [REQ-OPS-013](operations.md#req-ops-013-deploy-command-and-post-deploy-hooks), [REQ-SEC-011](security.md#req-sec-011-container-image-scanned-for-cves-before-deploy); all stay Implemented). PR checks run as parallel path-filtered lanes with a fail-closed backend test gate instead of one serial job, and deploys reuse the already-scanned container image when nothing it depends on changed, cutting typical pipeline time (per [AD112](../../documentation/decisions/README.md#ad112-ci-runs-as-parallel-path-filtered-lanes-and-deploys-reuse-content-addressed-container-images)).

- **Scripted e2e suite removed** (REQ-OPS-004 and REQ-OPS-015 deleted from `operations.md`). The full PR-check lane matrix now runs unconditionally once a night in addition to every pull request and manual dispatch, catching flaky tests and dependency drift between pushes.
