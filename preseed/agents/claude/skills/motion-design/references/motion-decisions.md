# Motion decisions

Read this before introducing substantial motion or defining how the selected thesis moves.

## Decide whether motion is warranted

Name the state, relationship, feedback, continuity, priority, or expressive purpose motion communicates. If removing it changes nothing users understand or feel, prefer stillness.

Consider frequency, attention, urgency, input method, device, task pressure, content length, and interruption. A repeated keyboard command, destructive confirmation, background status change, playful onboarding moment, and immersive transition should not share one duration or flourish.

## Derive character from direction

Translate the owner’s thesis into a small motion vocabulary: direct or elastic, quiet or emphatic, continuous or cut, spatial or tonal. Reuse that vocabulary instead of assigning a unique effect to every component.

Keep intensity where hierarchy earns it. Motion cannot rescue weak information architecture or art direction. Do not default to staggered entrances, scaled press states, bounce, blur, scroll reveal, trigger-origin transforms, centered modals, or one duration ceiling.

## Choose implementation conservatively

Prefer CSS, native transitions, or the incumbent framework for straightforward known-state motion. Use JavaScript, Web Animations, physics, timelines, or another runtime only when dynamic targets, interruption, synchronization, gesture coupling, or the selected experience requires them.

Inspect installed versions and current primary documentation before naming APIs. No implementation model is automatically compositor-only, off-main-thread, or smooth; property, browser, layer, workload, and runtime behavior decide.
