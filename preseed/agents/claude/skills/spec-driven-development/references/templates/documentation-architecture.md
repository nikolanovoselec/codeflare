## 5. Request Lifecycles

One numbered subsection per entry point identified by `sdd-init` Phase 6c. Entry points include: HTTP routes (or framework equivalents), cron / scheduled handlers, queue consumers, OS intent receivers, deep-link handlers, CLI entries, push notification handlers, WebSocket handlers. See `sdd-init/references/entry-point-probes.md` for the full per-stack catalog.

Each subsection follows the format:

### 5.N {Entry-point name}

{One-paragraph description of when this fires and what triggers it.}

```
{Entry-point trigger}
  └─► {Step 1 module / function}
       ├─ {substep}
       └─ {substep}
       │
       ▼
{Step 2 module / function}
  ├─ {happy path arrow}
  └─ {failure transition arrow with target state}
       │
       ▼
{Terminal step + outcome}
```

Implements [REQ-X-NNN](../sdd/{domain}.md#req-x-nnn-...) {and any other REQs along the flow}.

**Failure-transition coverage is mandatory.** Each lifecycle MUST show at least one failure transition (network error, validation rejection, auth expiry, etc.) — happy-path-only flow blocks miss the contributor's most common need: "what happens when X breaks?"

A scaffold with zero § Request Lifecycles subsections on a project with ≥1 detected entry point is a HIGH `scaffold-section-empty` finding.

## 8. Build and Deploy

Build-tool gotchas and non-obvious deploy-time behaviors that aren't covered by [`deployment.md`](deployment.md) (which carries the happy-path runbook). Examples:

- CSP / inline-script interactions (Astro, Next.js)
- Build-time vs runtime env var resolution (`--dart-define`, `--build-arg`)
- Source-mapped path coupling (Worker `applicationId` ↔ `intent://` package name)
- Asset-pipeline mirroring (`src/scripts/*.ts` ↔ `public/scripts/*.js`)

One subsection per gotcha. Skip the section entirely if the project has no non-obvious build/deploy interactions. Mandatory if any are detected.
